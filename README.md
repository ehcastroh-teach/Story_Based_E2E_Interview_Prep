# Titanic Survivor Analysis - Story-Based End-to-End Interview Prep

A complete, beginner-friendly data science pipeline built around one of the most famous datasets in history. This project teaches you how to move from raw passenger records to a working machine learning classifier - the same workflow you will encounter in data science interviews and on the job.

---

## Learning Objectives

By working through this notebook you will be able to:

- Load, inspect, and describe a real-world tabular dataset using pandas
- Identify and handle missing values using domain-informed imputation strategies
- Engineer new features from raw columns (titles extracted from names, family size, fare bands)
- Encode categorical variables as numeric representations for use in scikit-learn
- Store a preprocessed dataset in a SQLite database and reload it for modeling
- Train and evaluate five classification algorithms: Logistic Regression, KNN, SVM, XGBoost, and Random Forest
- Interpret feature importance scores from a Random Forest model
- Articulate why 100% accuracy is not always the goal when modeling data about people

### Key Columns in the Training Data

| Column | Description |
|---|---|
| `Survived` | Target variable: 1 = survived, 0 = did not survive |
| `Pclass` | Passenger class (1 = first, 2 = second, 3 = third) - a proxy for socioeconomic status |
| `Sex` | Passenger sex |
| `Age` | Passenger age in years (177 values missing; imputed by class and sex) |
| `SibSp` | Number of siblings or spouses aboard |
| `Parch` | Number of parents or children aboard |
| `Fare` | Ticket price |
| `Embarked` | Port of embarkation: C = Cherbourg, Q = Queenstown, S = Southampton |
| `Cabin` | Cabin number (roughly 77% missing; dropped in favor of Fare) |
| `Ticket` | Ticket number (unique per passenger; dropped as non-predictive) |

## Step-by-Step Walkthrough

### Why this dataset?

The Titanic dataset is popular for interviews because it is small enough to understand in full but rich enough to practice the full data science loop: exploration, cleaning, feature engineering, modeling, and interpretation. It also rewards domain knowledge - understanding the historical context of the disaster helps you build better features.

### Part 0 - Imports and Setup

All library imports are placed at the top of the notebook in a single cell. This is a best practice that makes dependencies visible and avoids import failures mid-run.

### Part 1 - Loading Data

The data is read from the `data/` directory using relative paths so the notebook runs correctly from any machine after a clean clone.

### Part 2 - Exploration

Before touching the data, we visualize distributions and check for class imbalance. The training set has 61.6% non-survivors. This is our baseline - any model that cannot beat 61.6% is worse than always predicting "did not survive."

### Part 3 - Preprocessing and Feature Engineering

**Why extract titles?** A passenger's title (Mr, Mrs, Miss, Master, Rare) encodes both sex and social status in a single compressed signal. It also helps impute age - a "Master" is almost always a child.

**Why impute age by Pclass and Sex?** Using a single global median would ignore the strong correlation between wealth (Pclass), sex, and age. Stratified imputation produces more realistic estimates.

**Why create `IsAlone`?** `FamilySize` has nine distinct values, many with very few observations. Collapsing to a binary "alone vs. not alone" retains the predictive signal while reducing noise.

**Why create `Age*Class`?** This interaction term captures the joint effect of being young and poor (high value) vs. old and wealthy (low value). It compresses two columns into one combined signal.

**Why drop Cabin?** Over 77% of cabin values are missing. The cabin tier (A through G) correlates with fare, which we keep - so dropping Cabin loses little information.

**Why dummy encode rather than ordinal encode for Embarked and Title?** These categories have no natural ordering, so treating them as integers (0, 1, 2) would introduce false ordinal relationships. Dummy columns avoid that assumption.

### Part 4 - SQLite Storage

Storing the preprocessed data in SQLite simulates a real production pattern: raw data lives in files or object storage, cleaned data lives in a relational store, and downstream consumers query that store. The round-trip query confirms the schema was written correctly.

### Part 5 - Model Comparison

We evaluate five algorithms on a held-out 20% validation split. All five cluster around 76-84%. The ceiling is roughly 80% because the survival of any individual passenger was partly determined by chance (who was near a lifeboat, which deck they were on, which crew members they encountered). See Appendix I for the human story behind this ceiling.

## Key Concepts Glossary

**Baseline accuracy** - The accuracy you would achieve by always predicting the majority class. For this dataset: 61.6%.

**Categorical encoding** - Converting non-numeric columns to numbers so that machine learning algorithms can use them. Two common approaches are ordinal encoding (for ordered categories) and one-hot / dummy encoding (for unordered categories).

**Class imbalance** - When one outcome class appears far more often than another in the training data. Can bias a model toward always predicting the majority class.

**Feature engineering** - Creating new input columns derived from existing ones using domain knowledge or mathematical transformations. Examples: extracting Title from Name, computing FamilySize from SibSp and Parch.

**Imputation** - Filling in missing values using statistical estimates (mean, median, mode) or model-based predictions rather than dropping rows.

**Interaction feature** - A new column formed by multiplying or combining two existing columns to capture their joint effect. Example: `Age*Class`.

**Label encoding** - Assigning an integer to each category. Appropriate only when the categories have a natural order (e.g., age bands 0-4).

**One-hot / dummy encoding** - Replacing a single categorical column with one binary column per category. Avoids implying a numeric ordering between categories.

**Ordinal feature** - A feature whose categories have a meaningful order (e.g., Pclass: 1 > 2 > 3 in prestige).

**Overfitting** - When a model learns the training data too closely and fails to generalize to new data.

**Train/validation split** - Dividing labeled data into a training set (used to fit the model) and a validation set (held out to estimate real-world performance).

**XGBoost** - Extreme Gradient Boosting; an ensemble method that builds many decision trees sequentially, each one correcting the errors of the previous.
