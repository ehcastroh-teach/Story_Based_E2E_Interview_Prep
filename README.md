# Titanic Survivor Analysis - Story-Based End-to-End Interview Prep

A complete, self-contained data science pipeline built around one of the most studied datasets in history. This project walks you from raw passenger records to a working multi-model classifier, stopping at every decision point to explain the reasoning - not just the code. The human stories woven throughout the notebook serve as a reminder that accuracy metrics describe real people, and that a model's ceiling can reflect irreducible randomness rather than a technical shortcoming. This is the same end-to-end workflow you will encounter in data science interviews and on the job.

---

## Learning Objectives

By working through this notebook you will be able to:

- Load, inspect, and describe a real-world tabular dataset using pandas
- Identify and handle missing values using both global and domain-stratified imputation strategies
- Engineer new features from raw columns (titles extracted from passenger names, family-size collapse to a binary flag, fare quartile bands, an age-by-class interaction term)
- Encode categorical variables correctly - dummy encoding for unordered categories, label encoding for ordered bands - and articulate why each choice matters
- Store a preprocessed dataset in a SQLite database and reload it with a SQL query for downstream modeling
- Train and compare five classification algorithms: Logistic Regression, KNN, SVM, XGBoost, and Random Forest
- Interpret feature importance scores from a Random Forest model
- Explain why a model's accuracy ceiling can reflect real-world randomness rather than a fixable technical failure

## Step-by-Step Walkthrough

### Why this dataset?

The Titanic dataset is a standard interview benchmark because it is small enough to understand end to end but rich enough to practice every stage of a real data science workflow: loading, exploration, cleaning, feature engineering, database storage, modeling, and interpretation. Crucially, survival was not random - it was shaped by social class, gender, age, and circumstance - which gives domain knowledge real predictive leverage.

### Part 0 - Imports and Setup

All library imports are placed at the top of the notebook in a single cell. This is a best practice that makes dependencies visible and prevents import failures mid-run. The random seed (`np.random.seed(1337)`) is set here so that the train/validation split is reproducible across machines.

### Part 1 - Loading Data

Both `train.csv` and `test.csv` are loaded into pandas DataFrames using relative paths from the `data/` directory. A combined list `combine = [train_df, test_df]` is created immediately so that preprocessing transformations can be applied to both sets in a single loop - avoiding the common mistake of transforming training data but forgetting to transform test data.

### Part 2 - Exploratory Data Analysis

Before modifying anything, the notebook visualizes feature distributions and checks for class imbalance. The training set is 61.6% non-survivors. This is the baseline: any model that cannot exceed 61.6% is worse than always predicting "did not survive." The EDA also computes survival rates broken down by both `Pclass` and `Sex` together, demonstrating how interaction effects matter more than individual features in isolation.

### Part 3 - Feature Engineering and Preprocessing

**Why extract titles from names?** A passenger's title (Mr, Mrs, Miss, Master, Rare) compresses both sex and social standing into a single signal. It also enables a useful sanity check: every "Master" in the dataset is male and young, confirming that the extraction is working as expected. Rare titles (Lady, Countess, Capt, Col, Dr, Major, Rev, Sir, Jonkheer) are grouped into a single "Rare" category because each appears too infrequently to estimate a stable survival rate. French feminine titles (Mlle, Mme, Ms) are normalized to their English equivalents before dummy encoding.

**Why impute age by Sex and Pclass?** Using a single global median would ignore the strong correlation between wealth, sex, and expected age. A "Master" in third class is unlikely to be the same age as a "Mrs" in first class. The stratified median produces more realistic estimates and reduces the risk that the imputed values distort downstream model coefficients.

**Why convert age to ordinal bands?** Age as a raw integer has 80 distinct values, many with only one or two observations. Binning into five equal-width bands (0-4) reduces noise and lets the model find a cleaner signal. Because age bands have a natural order (younger to older), label encoding - assigning integers 0 through 4 - is appropriate here. This is in contrast to unordered categories like Embarked or Title, where label encoding would imply a false numeric relationship.

**Why collapse FamilySize to IsAlone?** `FamilySize` (SibSp + Parch + 1) has nine distinct values, most with very few observations. The survival data shows a cleaner split between "alone" and "not alone" than across the full nine-value range. Collapsing to a binary flag retains the predictive signal while reducing noise.

**Why create Age\*Class?** This interaction term captures the joint effect of being young and poor (high product value) versus old and wealthy (low product value). In a linear model, individual features can only contribute additively; an interaction term lets the model capture their combined effect without requiring a more complex algorithm.

**Why dummy encode Embarked and Title but label encode Age and Fare bands?** Embarked and Title have no natural numeric ordering. Assigning integers (0, 1, 2) to C, Q, S would imply Southampton is "twice" Queenstown in some meaningful sense - which it is not. Dummy (one-hot) columns avoid that assumption. Age bands and Fare quartiles, by contrast, do have a natural order, so label encoding is appropriate and avoids the column-count explosion of dummy encoding.

**Why drop Cabin?** Over 77% of cabin values are missing. The notebook extracts cabin tier (the letter prefix A through G) and plots survival by tier to confirm it carries signal - then drops it anyway because the same tier-level information is largely captured by Fare, which is nearly complete.

### Part 4 - SQLite Storage

Writing the preprocessed training set to SQLite simulates a real production pattern: raw data lives in flat files or object storage, cleaned data lives in a relational store, and downstream consumers - including other team members - can query it directly without re-running the preprocessing pipeline. The round-trip query (`SELECT * FROM train_data`) confirms the schema was written and read back correctly. A Concept Check exercise asks the learner to write a SQL aggregation query to compare average Age and Fare between survivors and non-survivors.

### Part 5 - Model Building and Evaluation

Five algorithms are compared on a held-out 20% validation split. All five fall between 76% and 84%. The comparison follows the same three-step scikit-learn pattern for each: instantiate, fit, score. This consistency is deliberate - it means learners can focus on understanding what each algorithm does rather than on API differences.

The accuracy ceiling around 80% is not a tuning problem. Individual passenger survival was partly determined by chance: proximity to a lifeboat, which crew members happened to be nearby, which compartment a passenger was in when water entered. Appendix I illustrates this concretely with the stories of two real passengers whose outcomes contradicted their model-predicted survival probabilities. The lesson: when analyzing data about people, a model error is not always a failure - sometimes it is evidence of human agency operating beyond what structured data can capture.

The Random Forest also produces feature importance scores (mean decrease in impurity), showing which engineered features contributed most to predictions.

## Key Concepts Glossary

**Baseline accuracy** - The accuracy achieved by always predicting the majority class. For this dataset: 61.6%. Any model that cannot beat this number is not learning anything useful.

**Categorical encoding** - Converting non-numeric columns to numbers so machine learning algorithms can use them. The two approaches used here are dummy (one-hot) encoding for unordered categories and label encoding for ordered categories.

**Class imbalance** - When one outcome class appears far more often than another in the training data. In this dataset, 61.6% of passengers did not survive. Imbalance can bias a naive model toward always predicting the majority class.

**Concept Check** - A structured exercise cell embedded in the notebook where the learner writes code to answer a specific analytical question. Answers are provided in subsequent cells.

**Feature engineering** - Creating new input columns derived from existing ones using domain knowledge or mathematical transformations. Examples in this notebook: extracting Title from Name, computing FamilySize from SibSp and Parch, creating the Age\*Class interaction term.

**Imputation** - Filling in missing values with statistical estimates rather than dropping rows. This notebook uses a stratified median imputation for Age, grouped by Sex and Pclass.

**Interaction feature** - A new column formed by combining two existing columns to capture their joint effect. The `Age*Class` feature here compresses two columns into one combined signal that a linear model can use directly.

**Label encoding** - Assigning integers to ordered categories. Appropriate when categories have a meaningful rank (age bands 0-4, fare quartiles 0-3). Inappropriate for unordered categories.

**One-hot (dummy) encoding** - Replacing a single categorical column with one binary column per category. Used for Embarked and Title to avoid implying a false numeric ordering.

**Ordinal feature** - A feature whose categories have a meaningful order. Pclass (1 > 2 > 3 in prestige), AgeBand (0 = youngest), and FareBand (0 = lowest fare) are ordinal.

**Overfitting** - When a model memorizes the training data too closely and performs worse on new data. A large gap between training accuracy and validation accuracy is a common sign.

**Random seed** - A fixed starting value for a random number generator. Setting `np.random.seed(1337)` before the train/validation split ensures the same split is produced every time the notebook is run, making results reproducible.

**Train/validation split** - Dividing labeled data into a training set (used to fit the model) and a validation set (held out to measure real-world performance). This notebook uses an 80/20 split.

**XGBoost** - Extreme Gradient Boosting. An ensemble method that builds many decision trees sequentially, each one correcting the errors of the previous. Often the strongest performer on tabular classification tasks.
